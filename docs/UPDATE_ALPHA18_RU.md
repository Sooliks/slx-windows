# Обновление SLX VPN до 0.1.0-alpha.18

Дата подготовки: 24 октября 2026. Основа — предоставленный архив alpha.17, сверенный с `main` репозитория `Sooliks/slx-windows` (`491d9255d1a0cf32fd9eb679cb8887ca8df91d2f`). Это исправленные исходники Windows-клиента и конфигурация автоматического выпуска в GitHub Actions. Установщик собирается на Windows: в Actions либо на вашем ПК.

Владелец отправил исходники коммитом `58e3c92541641c453199ba6237b98f59f20f58d3`. Первый запуск Actions остановился до сборки на неверной проверке PE-версии `ISCC.exe`: это поле не соответствует основной версии Inno Setup. Исправленный workflow проверяет официальный баннер Inno Setup 6 и штатный код возврата команды `/?`. Проверки приложения и сборка установщика в первом запуске не выполнялись; релиз alpha.18 ещё не опубликован.

Прямая отправка исправления из этой сессии по-прежнему недоступна: GitHub-подключение ранее вернуло `403 Resource not accessible by integration`. После применения патча создайте новый коммит и выполните push из своей Git-копии. Изменение самого `release.yml` теперь также запускает выпуск, без повышения версии приложения. Не перезапускайте старую неудачную задачу: она использует старый коммит.

## 1. Применить файлы

Скопируйте содержимое папки `slx-windows` из архива `source-changed` в корень существующего проекта с заменой файлов, включая `.github`. Полный архив содержит все исходники для восстановления контекста и существующую конфигурацию CI из GitHub; старые `bin`, `obj`, `.tmp`, результаты тестов и установщики не включены. Удалять исходные файлы не требуется.

Команды выполняются из корня существующей Git-копии `Sooliks/slx-windows`. Проверьте:

```powershell
git rev-parse --show-toplevel
git status --short
```

Если исходники просто распакованы и `.git` отсутствует, сначала создайте рабочую копию в новой папке и примените патч туда:

```powershell
git clone https://github.com/Sooliks/slx-windows.git slx-windows-alpha18
Set-Location .\slx-windows-alpha18
```

Патч рассчитан на alpha.17. Сохраните собственные незакоммиченные изменения перед заменой. Не создавайте новую Git-историю для публикации поверх существующего проекта. Если в репозитории уже более новая версия, совместите правки, не заменяя весь проект вслепую.

Для автоматического выпуска из раздела 5.1 локально нужны Git и ваш обычный доступ на запись в репозиторий. Windows runner в GitHub выполняет сборку и проверки.

Для ручной сборки нужны прежние инструменты: Windows 10 19041+/11 x64, PowerShell 7, .NET SDK **10.0.401**, Inno Setup 6. Готовым пользователям .NET отдельно не нужен — он входит в установщик. Для ручной публикации также нужен Node.js и настроенный доступ Git к GitHub.

## 2. Проверить и собрать установщик для своего ПК и друзей

```powershell
pwsh -NoProfile -File .\scripts\verify.ps1
if ($LASTEXITCODE -ne 0) { throw 'Проверки не прошли.' }

pwsh -NoProfile -File .\scripts\build.ps1 -Candidate
if ($LASTEXITCODE -ne 0) { throw 'Установщик не собран.' }
```

Кандидат появится в:

```text
artifacts\candidates\0.1.0-alpha.18\<дата-и-ID>\output\SLX-VPN-0.1.0-alpha.18-win-x64-setup.exe
```

Открыть папку самого нового кандидата:

```powershell
$setup = Get-ChildItem .\artifacts\candidates\0.1.0-alpha.18 -Recurse -Filter 'SLX-VPN-0.1.0-alpha.18-win-x64-setup.exe' |
    Sort-Object LastWriteTime -Descending | Select-Object -First 1
if (-not $setup) { throw 'Установщик кандидата не найден.' }
explorer.exe $setup.DirectoryName
```

Отключите VPN кнопкой «Отключиться», полностью закройте SLX через трей и установите `.exe` поверх alpha.17. Не копируйте отдельные DLL в `Program Files`: служба и интерфейс обновляются вместе. Подписка и список приложений сохраняются. Кандидат подходит для ручной проверки, но намеренно не допускается скриптом к публикации через канал обновлений.

Если `pwsh` не найден, откройте установленный PowerShell 7 или используйте полный путь `C:\Program Files\PowerShell\7\pwsh.exe`. Если Inno Setup стоит в другом месте, передайте `-InnoCompiler 'C:\...\ISCC.exe'`. Не отключайте защиты Windows и не меняйте закреплённые версии для обхода ошибки сборки.

## 3. Проверка на проблемном компьютере

1. В интерфейсе должна отображаться `0.1.0-alpha.18`. Службу можно проверить командой `Get-Service SLXVPN`.
2. Проверьте обычный интернет при отключённом SLX. Затем выберите «Приложения» и оставьте один браузер. CS2 и Steam не включайте в VPN для проверки прямого подключения.
3. Подключите Hysteria2. Проверьте браузер, затем CS2. Отдельно попробуйте VLESS/XHTTP из подписки, если Hysteria2 не подключается. На ПК с Ethernet/Wi-Fi проверьте работу без удаления или отключения адаптеров.
4. Нажмите «Отключиться» во время подключения: оно должно прерваться, завершить очистку и вернуть подтверждённое отключённое состояние. Проверьте интернет после отключения.
5. Если первый запуск завершился определённой ошибкой, после успешной очистки должна остаться ошибка с состоянием «Не подключено», а не бесконечное восстановление новой попытки.
6. Если проблема сохраняется, скопируйте данные из «Помощь → Копировать диагностику». Нужны версия, код, режим, протокол, включён ли ExitLag и наблюдение: не работает только CS2 или весь интернет. Личную ссылку подписки присылать не нужно.

Уже работавший VPN при обрыве сохраняет защиту. Потерянный ответ службы также не разрешает автоматическое снятие блокировки: нажмите «Отключиться». Публичный системный DNS общий для программ и по-прежнему идёт через VPN; при восстановлении он способен влиять на CS2/Steam, даже если они не выбраны. Исправления не являются доказательством полного разделения DNS и UDP-трафика игр.

## 4. Если служба недоступна и обычное отключение не помогает

Это **явное отключение VPN и его защиты**. Полностью выйдите из SLX через меню трея. Откройте **Windows PowerShell от имени администратора**, перейдите в папку проекта с патчем и выполните:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\repair-network.ps1
```

Скрипт из патча работает и с установленной alpha.17; новая сборка для этого не требуется. После установки alpha.18 его копия также доступна здесь:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File 'C:\Program Files\SLX VPN\scripts\repair-network.ps1'
```

Скрипт проверяет фиксированный путь службы, останавливает её, дожидается удаления TUN по присутствию устройства, вызывает штатное удаление только SLX-фильтров/намерения подключения, очищает кэш DNS и запускает службу без подключения. Подписка и настройки остаются. Другие VPN, общий firewall, системные DNS-настройки и маршруты физических адаптеров не сбрасываются. `ExecutionPolicy Bypass` действует только на этот запуск PowerShell и не отключает Defender.

Если остановка/идентификация/удаление адаптера не подтверждены, скрипт завершится ошибкой и не заявит об успехе. При зависшем собственном ядре/адаптере перезагрузите Windows и повторите восстановление. Не используйте сброс всего firewall, всех адаптеров или принудительное завершение всех процессов `xray.exe`.

## 5. Опубликовать обновление в GitHub

### 5.1. Автоматическая сборка и публикация после push

Прежний `verify.yml` выполнял только проверки на pull request или при ручном запуске. Новый `.github/workflows/release.yml` собирает и публикует выпуск при изменении `Directory.Build.props` или самого workflow в `main`, а также допускает ручной запуск из вкладки Actions. Версия в патче уже поднята до `0.1.0-alpha.18`; исправление workflow запускает новую попытку выпуска с этой же версией.

После применения патча проверьте `git diff`, убедитесь, что в рабочей копии нет посторонних изменений, и выполните из корня проекта в PowerShell:

```powershell
git diff --stat
git add -- .github/workflows/release.yml Directory.Build.props PROJECT_SPEC.md README.md SECURITY.md docs scripts src tests
if ($LASTEXITCODE -ne 0) { throw 'Файлы не добавлены.' }

git commit -m 'Release alpha.18: network recovery and Windows release automation'
if ($LASTEXITCODE -ne 0) { throw 'Коммит не создан.' }

git push origin HEAD:main
if ($LASTEXITCODE -ne 0) { throw 'Изменения не отправлены в main.' }
```

Если Git отклоняет push из-за более новой истории, сначала совместите изменения. Не используйте force-push. Существующий `verify.yml` остаётся в репозитории.

Откройте `https://github.com/Sooliks/slx-windows/actions` и дождитесь успешного завершения workflow выпуска. Он выполняет locked restore, сборку и полный набор Windows-тестов, затем собирает установщик штатным `build.ps1`, упаковывает исходники относительно `v0.1.0-alpha.17` и публикует prerelease через `release.mjs`. Локальные .NET SDK и Inno Setup для этого пути не нужны. Токен Actions выдаётся только задаче выпуска; исходники и архивы не содержат токенов.

При ошибке тестов, сборки, версии, чистоты исходников или контрольных сумм публикация останавливается. Исправьте показанную причину и запустите workflow вручную на актуальном `main`. Уже опубликованные релизы и их файлы не перезаписываются.

После успешного выполнения проверьте `https://github.com/Sooliks/slx-windows/releases/tag/v0.1.0-alpha.18`: должны присутствовать установщик и пять сопутствующих файлов, перечисленных ниже. Затем проверьте страницу `https://slxvpn.com/windows?lang=ru` и кнопку скачивания: она должна перейти на установщик alpha.18. До публикации сайт возвращал alpha.17; окончательное переключение ссылки и внутренний кеш сайта из этой сессии проверить нельзя.

### 5.2. Ручная сборка и публикация с Windows ПК

После успешных Windows-проверок проверьте `git diff`, добавьте только изменения этой версии и создайте коммит. Не включайте другие незавершённые изменения в коммит выпуска.

```powershell
git diff --stat
git add -- .github/workflows/release.yml Directory.Build.props PROJECT_SPEC.md README.md SECURITY.md docs scripts src tests
git commit -m 'Release alpha.18: responsive control and safe failed-connect recovery'
if ($LASTEXITCODE -ne 0) { throw 'Коммит не создан.' }
if (git status --porcelain) { throw 'Для выпуска нужна чистая рабочая копия.' }

pwsh -NoProfile -File .\scripts\build.ps1
if ($LASTEXITCODE -ne 0) { throw 'Сборка выпуска не прошла.' }

pwsh -NoProfile -File .\scripts\package-source.ps1 -BaseRef v0.1.0-alpha.17
if ($LASTEXITCODE -ne 0) { throw 'Упаковка выпуска не прошла.' }
```

Результат: `artifacts\release\0.1.0-alpha.18`. В нём ровно шесть файлов: установщик, полный и изменённый ZIP исходников, `DELETIONS.txt`, `provenance.json`, `SHA256SUMS.txt`. Скрипты проверяют чистый коммит, версию, соответствие установщика и контрольные суммы. Старые выпуски не перезаписываются, кандидаты не публикуются. Если отсутствует прошлый тег, выполните `git fetch origin --tags` и повторите упаковку. Не меняйте защитные проверки и provenance вручную.

При наличии нового workflow push версии в `main` также запускает автоматический выпуск. Не запускайте локальный uploader одновременно с Actions: выберите один способ публикации. Для ручного пути сначала отмените/отключите соответствующий автоматический запуск в Actions, затем выполняйте команды после проверки установщика:

```powershell
git push origin HEAD:main
if ($LASTEXITCODE -ne 0) { throw 'Исходники не отправлены на GitHub.' }

node .\scripts\github.mjs status
if ($LASTEXITCODE -ne 0) { throw 'Не подтверждён доступ к GitHub.' }

node .\scripts\release.mjs
if ($LASTEXITCODE -ne 0) { throw 'Выпуск не опубликован; проверьте показанный код.' }
```

При локальном запуске `release.mjs` использует существующие Git-учётные данные владельца. В Actions используется отдельная проверка фиксированных репозитория, ветки, события и точного коммита. Оба пути сохраняют prerelease-статус и проверки происхождения/контрольных сумм пакета. Токены в исходники/чат добавлять не нужно. Если Git откажет в обычном push, совместите актуальные изменения; не используйте force-push.

После публикации alpha.17 сможет предложить alpha.18 при ручной проверке обновлений или следующей штатной проверке. Скачивание и запуск установки остаются действиями пользователя. Одного размещения ZIP исходников недостаточно: нужны установщик с версией и `SHA256SUMS.txt` по контракту updater.

## Проверки и ограничения

Фактические команды и результаты — в `docs/VERIFICATION.md`. Linux-кросс-сборка и переносимые тесты не исполняют WPF, Windows Service, WFP, Wintun и Inno Setup. Первый Actions workflow запустился после push владельца, но остановился на проверке Inno до тестов приложения и сборки. Новый запуск с исправлением ещё необходим. Успешная сборка/тесты в Actions также не заменяют проверку подключения и CS2 на проблемных Windows-ПК.
