# SLX VPN alpha.28 — исправление восстановления и выпуск обновления

Подготовлено 6 ноября 2026 года. База: `v0.1.0-alpha.27`, коммит
`b140056bc92c95f12bc37349e15299de9a44c05e`. Новая версия исходников: `0.1.0-alpha.28`, FileVersion `0.1.0.28`.
Фактические результаты проверок находятся в [VERIFICATION.md](VERIFICATION.md). Подготовленные исходники ещё не
означают опубликованный установщик или подтверждённое устранение сбоя на ПК друга.

## Что произошло и что исправлено

В снимке друга от 6 ноября сначала не прошли все три проверки VPN: основная, повторная и запасная. Последнее
восстановление зарегистрировано в 15:42:26 МСК, а новое подключение и startup DNS — в 15:43:15. Он сообщил,
что ничего не нажимал. По реализации alpha.27 новый startup DNS указывает на полный запуск, но снимок после
восстановления не объясняет точную причину этого запуска и не измеряет длительность потери интернета во всём ПК.

У владельца другой снимок: DNS остался от старого запуска, последнее восстановление прошло примерно за 1,2 секунды,
а повторная и запасная проверки связи завершились успешно. Работоспособность одного ПК не исключает другой путь
восстановления на другом ПК. Счётчик `Health incidents` не равен числу переподключений.

Позже у владельца тоже был краткий обрыв, но только выбранных приложений: примерно 16:10:03 → 16:10:06 МСК,
с прежним startup DNS и Attempt 2 / HEALTH_PROBE_FAILED. Это согласуется с перезапуском отдельного ядра. Интервал
между этими наблюдениями около 2,24 секунды не измеряет весь обрыв; сохранённый снимок маршрутов был сделан раньше.

В alpha.27 невыбранные приложения используют прямой выход к провайдеру, но тоже проходят через общий локальный TUN.
Поэтому лишнее пересоздание этого процесса может затронуть весь ПК. В alpha.28:

- Ошибки отдельного VPN-ядра больше не делают исправный TUN кандидатом на полный перезапуск сами по себе.
  Область восстановления выбирается до проверки и запуска ядра; его ошибка остаётся в этой области.
- Полное восстановление сохраняется при потере общего процесса, адаптера, данных о локальных портах или маршрутов.
  Недействительное базовое состояние защиты Windows явно требует полного восстановления.
- После перезапуска только ядра обычные маршруты проверяются перед подтверждением «Подключено».
- Диагностика показывает версию службы и до 16 последних событий восстановления с причинами и поколениями процессов.

Серверы, DNS-политика, runtime, драйвер, проверочные адреса, тайм-ауты и интервалы повторов не менялись.
Эта версия не гарантирует отсутствие обрывов при отказе самого TUN, физической сети или сервера. Автоматическое
переключение на VLESS при блокировке UDP остаётся отдельной проверкой: её не удалось подтвердить в приёмке alpha.27.

## 1. Применить изменённые файлы

Используй существующий репозиторий `C:\Users\xls\Desktop\slx-windows`, связанный с
`https://github.com/Sooliks/slx-windows.git`. Перед копированием сохрани свои незакоммиченные изменения отдельно,
если они есть. Архив исправления рассчитан на указанную точную базу alpha.27.

Распакуй архив изменённых файлов. Скопируй **содержимое его папки `slx-windows`** в существующую папку проекта,
с заменой одноимённых файлов. Не создавай вложенную папку `slx-windows\slx-windows`.
Новые файлы тоже нужны: одного изменения номера версии недостаточно.

Полный архив содержит полный снимок исходников с тем же корнем `slx-windows` и нужен для контекста или отдельной
проверки. Он не заменяет Git-историю существующего checkout. Архивы исходников не являются установщиками.

## 2. Проверить точную базу и новую версию

Этот блок запускается в обычном Windows PowerShell **после копирования файлов**, до commit. Для отправки исходников
нужен Git; устанавливать .NET, Node.js и Inno Setup на этот ПК ради push не требуется — сборку выполнит Windows CI.

```powershell
Set-Location "$env:USERPROFILE\Desktop\slx-windows" -ErrorAction Stop

$expectedBase = 'b140056bc92c95f12bc37349e15299de9a44c05e'
$originUrl = git remote get-url origin
if ($LASTEXITCODE -ne 0) { throw 'Не удалось проверить origin' }
if ($originUrl -notin @('https://github.com/Sooliks/slx-windows.git', 'git@github.com:Sooliks/slx-windows.git')) {
    throw 'Открыт другой репозиторий: нужен Sooliks/slx-windows'
}

git fetch origin main --tags
if ($LASTEXITCODE -ne 0) { throw 'Не удалось получить состояние GitHub и теги' }

$head = git rev-parse HEAD
if ($LASTEXITCODE -ne 0) { throw 'Не удалось проверить локальный коммит' }
if ($head -ne $expectedBase) { throw 'Локальная база отличается от alpha.27 b140056; не применяй этот патч вслепую' }

$remoteHead = git rev-parse origin/main
if ($LASTEXITCODE -ne 0) { throw 'Не удалось проверить origin/main' }
if ($remoteHead -ne $expectedBase) { throw 'main на GitHub изменился; сначала нужно согласовать изменения с новой базой' }

$previousTag = git rev-parse --verify 'v0.1.0-alpha.27^{commit}'
if ($LASTEXITCODE -ne 0) { throw 'Не найден тег предыдущего выпуска alpha.27' }
if ($previousTag -ne $expectedBase) { throw 'Тег alpha.27 не соответствует ожидаемой базе' }

[xml]$buildProps = Get-Content .\Directory.Build.props -Raw -ErrorAction Stop
if ($buildProps.Project.PropertyGroup.Version -ne '0.1.0-alpha.28' -or
    $buildProps.Project.PropertyGroup.FileVersion -ne '0.1.0.28') {
    throw 'Исправление alpha.28 не применено или открыта другая папка'
}

git status --short
if ($LASTEXITCODE -ne 0) { throw 'Не удалось проверить рабочую папку' }
git diff --stat
if ($LASTEXITCODE -ne 0) { throw 'Не удалось проверить изменения' }
```

Проверь список перед следующим блоком: это должны быть исправления alpha.28 и новые файлы из архива.
Если проверка базы остановилась, сохрани текущую работу и сравни её с новой базой. Не используй `reset --hard`,
force-push или принудительную замену тега, чтобы пройти эту проверку.

## 3. Отправить обновление в main

После проверки списка выполни:

```powershell
git add -- Directory.Build.props PROJECT_SPEC.md README.md docs src tests
if ($LASTEXITCODE -ne 0) { throw 'Не удалось добавить исправления alpha.28' }

git diff --cached --stat
if ($LASTEXITCODE -ne 0) { throw 'Не удалось проверить подготовленный коммит' }

git commit -m 'Release alpha.28: preserve shared TUN during core recovery'
if ($LASTEXITCODE -ne 0) { throw 'Не удалось создать коммит alpha.28' }

git push origin HEAD:main
if ($LASTEXITCODE -ne 0) { throw 'Не удалось отправить alpha.28 в GitHub' }
```

Изменение `Directory.Build.props` в `main` запускает существующий workflow
**[Publish Windows prerelease](https://github.com/Sooliks/slx-windows/actions/workflows/release.yml)**.
Он использует именно отправленный коммит, сам находит предыдущий тег `v0.1.0-alpha.27`, выполняет locked restore,
сборку, тесты и проверки исходников, затем собирает установщик и публикует неизменяемые assets.
Ручной тег и ручная загрузка установщика не нужны. Не запускай `release-base.mjs` до нового commit: тогда HEAD ещё
равен предыдущему релизу, и проверка закономерно откажет.

Дождись зелёного workflow именно для нового коммита. Если он упал, релиз не считай готовым: нужно прочитать ошибку
и исправить её, сохранив обязательные проверки. Повторная отправка одной и той же версии не должна заменять уже
опубликованные assets.

## 4. Проверить публикацию и сайт

В [GitHub Releases](https://github.com/Sooliks/slx-windows/releases) должен появиться `v0.1.0-alpha.28` с шестью файлами:

1. `SLX-VPN-0.1.0-alpha.28-win-x64-setup.exe`
2. `SLX-VPN-0.1.0-alpha.28-source-full.zip`
3. `SLX-VPN-0.1.0-alpha.28-source-changed.zip`
4. `DELETIONS.txt`
5. `provenance.json`
6. `SHA256SUMS.txt`

Это выпуск существующего канала предварительных версий. Коммит на GitHub, зелёные тесты и опубликованный installer
— разные этапы. Для ручного скачивания используй installer из этого релиза; встроенное обновление отдельно читает
каталог GitHub и проверяет пакет по контрольной сумме.

Проверить, куда ведёт кнопка сайта:

```powershell
curl.exe --noproxy "*" --max-time 20 -sS -D - -o NUL -H "Cache-Control: no-cache" "https://slxvpn.com/download/windows" |
    Select-String '^(HTTP/|Location:)'
if ($LASTEXITCODE -ne 0) { throw 'Не удалось проверить редирект сайта' }
```

Ожидается `302` и `Location` на
`https://github.com/Sooliks/slx-windows/releases/download/v0.1.0-alpha.28/SLX-VPN-0.1.0-alpha.28-win-x64-setup.exe`.
Пока workflow не закончил публикацию, прежняя версия по ссылке ожидаема. Если релиз уже опубликован, а `Location`
по-прежнему содержит alpha.27, это отдельное состояние сайта или его кэша; успешное обновление в приложении
не подтверждает актуальность редиректа. Не заменяй старый installer новым под прежним именем.

## 5. Установить и проверить у друга

Обнови интерфейс и службу вместе штатным установщиком или встроенным обновлением. Во встроенном процессе загрузка
не отключает активный VPN; явная установка с отключением требует соответствующего действия в приложении. При ручном
запуске установщика сначала явно отключи SLX и дождись подтверждённого отключения. Подписка и настройки сохраняют
прежние хранилища; удалять профиль или делать общий сброс сети не требуется.

После установки скопируй диагностику. Начало отчёта и `Service version` должны показывать alpha.28.
`Service observation: current` означает свежий ответ службы, а не доказательство доставки пакетов всех приложений.
Для повторения случая нужны следующие наблюдения:

- Обычная работа в «Выбранных приложениях»: выбранное приложение действительно выходит через VPN, невыбранное —
  напрямую. Проверь и TCP, и используемый приложением UDP. Одного статуса «Подключено» недостаточно.
- Оставь невыбранное приложение с длительным соединением, например поток, и выбранное приложение активными.
  Если сбой повторится сам, сразу скопируй отчёт, по возможности до ручного отключения. После этого можно явно
  отключить SLX, если нужно вернуть связь; сохрани и следующий отчёт. Запиши время и какие приложения потеряли сеть.
- При повторных ошибках только VPN-ядра ожидается `scope=VpnCore`: поколение TUN сохраняется, а поколение ядра
  увеличивается при успешном запуске нового процесса. Проверка реального невыбранного потока должна подтвердить,
  что он не оборвался; одни счётчики этого не доказывают.
- `scope=FullTunnel` требует рассмотрения причины: FrontUnavailable, AdapterUnavailable, LocalLinkUnavailable,
  TrafficRouteFailed или ProtectionBaselineInvalid описывают отдельные основания полного восстановления.
  Явное новое подключение тоже запускает полный TUN. В исходном снимке alpha.27 такой истории ещё не было.

Проверку с принудительной остановкой процессов, исчезновением адаптера, изменением маршрутов или native-защиты
проводят отдельно в контролируемой Windows-сессии. Не останавливай общий TUN и не добавляй блокировки firewall на
рабочем ПК друга только ради сбора диагностики. Нужны проверки, что независимая неисправность действительно требует
полного восстановления, защита остаётся действующей, а «Подключено» не появляется раньше подтверждённых маршрутов.

Если проблема повторяется только с Hysteria2, можно отдельно сравнить доступный в подписке VLESS той же локации:
явно отключить SLX, выбрать его и подключиться. Запиши транспорт, время и результат. Это сравнение помогает отличить
транспортные условия; оно не доказывает причину предыдущего сбоя, автоматический fallback или гарантированное решение.

Если восстановление надолго застряло с ошибкой запуска ядра, сначала сохрани диагностику, затем нажми «Отключить»,
дождись подтверждённого отключения и подключись заново. Такой запуск выделяет новые локальные порты; обычное
«Переподключить» может использовать прежние. Alpha.28 не определяет по одному коду CORE_* зависший общий процесс
или порт, занятый другой программой, и не обещает автоматически исправить эти отдельные случаи.

### Как читать новую историю

`Lifecycle since UTC` задаёт период памяти службы; история ограничена 16 последними событиями и не является
постоянным журналом. `AutomaticRecovery` обозначает автоматический путь службы, `ConnectRequest`/`ReconnectRequest`
— путь запроса, `ServiceRestore` — восстановление намерения службой. Запрос мог поступить из логики приложения,
поэтому его наличие само по себе не означает нажатие человеком.

`Started`, `Connected`, `Failed`, `Cancelled` — наблюдённые стадии операции. `tun_generation` и `core_generation`
считают запущенные процессы в текущем периоде, а не длительность сетевой непрерывности. Отсутствие необязательного
`code` не доказывает отсутствие ошибки: в отчёт допускается только ограниченный список безопасных кодов.
При выключенном VPN поле истории не передаётся, чтобы старый помощник обновления мог прочитать ответ новой службы.

## Локальная проверка кандидата для разработчика

Если на Windows уже установлены требуемые SDK из `global.json`, PowerShell 7 и Inno Setup 6, кандидат можно собрать
перед отправкой. Эти команды не публикуют релиз и не заменяют установленную сетевую приёмку:

```powershell
pwsh -File .\scripts\verify.ps1
if ($LASTEXITCODE -ne 0) { throw 'Проверка alpha.28 не прошла' }

pwsh -File .\scripts\build.ps1 -Candidate
if ($LASTEXITCODE -ne 0) { throw 'Не удалось собрать кандидата alpha.28' }
```

Путь к кандидату печатает сборка в `artifacts/candidates/...`; файлы кандидата не подменяют release assets.
Для обычного выпуска достаточно commit/push и успешного Windows workflow из шагов выше.

Если потребуется вернуться на alpha.27, сначала явно отключи SLX и используй её опубликованный установщик.
Автоматическое обновление не выполняет downgrade. Старые исходники и пакет alpha.27 сохраняют старый дефект
восстановления; возврат сам по себе не устанавливает причину инцидента.
